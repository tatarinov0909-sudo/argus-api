# Предварительная проверка импорта остатков

Исполняемое общее ядро и CLI для разработчика адаптеров. Они читают файл
`argus.inventory` v1 и состояние назначения, возвращают замечания либо план
изменений. **В 1С ничего не записывается. Готового загрузчика 1С здесь нет.**
Новых зависимостей, сети, базы данных и рабочего `.env` не требуется.

Из корня API, на искусственном примере с фиксированным временем:

```powershell
node tools/inventory-import/cli.js docs/argus-inventory-v1.example.json tools/inventory-import/context.example.json 2026-09-10T10:10:00.000Z
node --test test/inventory-import-planner.test.js
```

Для настоящего файла третий аргумент опускается: используется текущее время.
CLI принимает UTF-8 JSON, включая BOM, до 25 МиБ на файл. Ничего не сохраняет;
результат пишет в stdout. Коды выхода: `0` — план готов или уже применён,
`2` — проверка заблокировала план, `1` — ошибка чтения или аргументов.

## Вход от будущего адаптера

`context.example.json` показывает форму входа, только тестовые данные.

- `binding`: сохранённая связь компании/склада Аргуса с одной целевой базой,
  организацией и складом; назначение только `salesAvailability`.
- `policy`: явно настроенный допустимый возраст снимка, каждого наблюдения
  складского остатка и каталога назначения. Числа в примере не являются
  утверждённым SLA. Неизвестное время наблюдения блокирует план.
- `catalog`: свежий каталог выбранного назначения со строковым штрихкодом,
  ID номенклатуры, ID характеристики (или `null`), единицей и текущим
  доступным для продажи количеством. Штрихкод не преобразуется в число.
- `journal`: применённые снимки с `sellerId`, `warehouseId`, `target`,
  `snapshotId`, `generatedAt`; при первом подключении `[]`. Записи других
  источников и назначений не считаются повторами текущего импорта.

Один штрихкод должен соответствовать ровно одной номенклатуре/характеристике
в штуках. Два исходных штрихкода, указывающие на одну целевую позицию, тоже
блокируются: количества не складываются. Товары, которых нет в снимке,
остаются без изменений. Каталог с ценами, токенами или другими секретами
этому инструменту не нужен.

## Результат

- `blocked`: есть замечания, `changes` всегда пуст. Частичный импорт запрещён.
- `already_applied`: этот снимок уже есть в журнале текущей связи, изменений нет.
- `ready_for_adapter`: весь снимок проверен, `changes` содержит абсолютные
  `before`/`after` только для доступности продаж. Совпавшие количества
  учитываются в `unchangedCount`.

`onHand`, `inAssembly` и `available` сохраняются раздельно. Ядро проверяет
`available = max(0, onHand - inAssembly)` и никогда не предлагает записать
`available` в физический или бухгалтерский остаток. SHA-256 сверяется с
контрактом реального экспортера; это проверка содержимого, не цифровая подпись
и не подтверждение подлинности файла. `generatedAt` намеренно не входит в
этот хеш, поэтому свежесть исходных складских событий проверяется отдельно.

## Что остаётся адаптеру конфигурации

Нужен один проверенный адаптер на поддерживаемое семейство конфигураций,
повторно используемый всеми его продавцами. Он определяет совместимость,
читает каталог/характеристики/единицы и журнал, выбирает согласованное место
хранения доступности продаж. Нельзя угадывать регистр по названию или
использовать бухгалтерский остаток как замену доступности.

Предварительный план не блокирует данные 1С. Перед применением адаптер должен
в транзакции повторно проверить журнал и текущие `before`, получить блокировку
области назначения и записать весь снимок вместе с записью журнала атомарно.
Изменившееся состояние требует нового предварительного расчёта. Привязка
должна исключать перезапись одного назначения разными источниками либо
хранить источники раздельно. Изменение физического остатка, пересчёт упаковок,
новые карточки и объединение нескольких складов этим планом не предусмотрены.

Совместимость можно объявлять после проверки адаптера на отдельной базе:
повтор, устаревший файл/каталог, конкурирующий импорт, характеристики,
упаковки, ноль, несколько складов, ошибки и откат всей транзакции.
