# Команды приложения грузчика

Контракт версии 1 добавляется поверх существующих маршрутов. Бизнес-правила
и границы приложения определяются основным продуктовым репозиторием.

## Поддержка сервера

`GET /api/worker/capabilities` (грузчик, владелец, менеджер) возвращает:

- `offline.version = 1`;
- `offline.idempotentOperations` — массив `{method, path}` с шаблонами маршрутов;
- `offline.supportedOperations` — отдельный список действий, которые можно
  сохранить без связи: приёмка позиции, дополнительная раскладка, пауза/возврат;
- `offline.maxPendingStockCommands = 1` — ограничение клиентской очереди;
- `cellQr.version = 1`, `cellQr.prefix = "argus:cell:v1:"`.

Отсутствие capability означает, что клиент сохраняет черновик и требует связь.
Наличие идемпотентности само по себе не разрешает исполнение действия офлайн.

## Повтор запроса

Для поддержанных POST клиент создаёт UUID **до первого запроса** и передаёт
его в `X-Argus-Operation-Id`. Повтор использует тот же ID, адрес, параметры,
тело и значение `X-Argus-Offline`. Последний заголовок равен `1` для команд,
сохранённых по офлайн-контракту. Заголовок нельзя добавлять только на повторе.

В одной транзакции записываются идентификатор, сотрудник и склад из
авторизации, хеш запроса, результат и складское изменение. Одновременные
повторы ожидают завершения первого запроса. Повтор выполненного действия
возвращает исходный результат и `X-Argus-Operation-Replayed: 1`. Изменённые
данные или другой сотрудник с тем же ID получают `409 operation_changed`.
Ошибка, откатившая транзакцию, не оставляет подтверждение команды.

Старый браузер без заголовка продолжает работать по прежнему контракту.
Неподдержанный офлайн-маршрут получает `409 offline_not_supported`.
Права и действительность ключа проверяются и для повторов.

После доставки очереди клиент перечитывает текущее состояние: сохранённый
ответ описывает результат исходного запроса, а не все последующие действия.
История подтверждений не имеет автоматического срока удаления. Удалять её
при ещё возможных повторах нельзя. Миграция запрещает откат схемы, если
история уже используется; прежний код приложения совместим с новой схемой.

## Приёмка и раскладка без связи

К обычному телу `POST /api/receiving` добавляются:

- `workSessionId` — `assembly.id` из подтверждённого начала работы;
- `occurredAt` — ISO-время подтверждения с учётом смещения к `serverNow`,
  записанное один раз до помещения команды в очередь;
- `expected: {received: false}`;
- `cellQr` рядом с `cellBlockId`, либо в каждом элементе `placements`;
- для брака при приёмке — `defect.cellQr` рядом с `defect.cellBlockId`.

Для `POST /api/receiving/items/:invoiceItemId/place`:

- `workSessionId`;
- `occurredAt` — время подтверждения по тем же правилам;
- `expected: {unplacedQty: N}` — полученный от сервера остаток неразложенного;
- `cellQr` вместе с выбранным `cellBlockId`.

Пустая приёмка (`acceptedQty: 0`) не требует скана. Сервер под блокировкой
проверяет принадлежность текущего активного захода, ожидаемый остаток,
склад и существование ячейки, совпадение скана с выбранным местом и режим
адресного хранения. При конфликте команда не применяется: клиент сохраняет
её для сверки и не генерирует новый ID для автоматического повторения.

Время подтверждения обязательно для офлайн-команд: оно не может быть раньше
последнего события своего захода или больше чем на минуту впереди сервера.
Если именно эта команда завершает свой заход, время окончания и длительность
работы считаются по `occurredAt`; ожидание доставки не добавляется ко времени
работы. Чужой или ранее завершённый заход этим временем не переписывается.
Сервер сохраняет отдельно время события и время получения команды.

Это ограниченный офлайн: заранее открытая работа и один неподтверждённый
складской шаг. Резервирование товара для длительной работы без связи,
автоматическое объединение конфликтов, офлайн-отбор, возвраты, перемещения
и работа с браком отдельными командами пока не заявлены в capabilities.
Данные устройства до подтверждения сервером показываются как сохранённые
на устройстве, а не проведённые складские операции.

## QR ячеек

`GET /api/worker/cells/:id/qr` возвращает `{cellBlockId, label, qr}`.
`POST /api/worker/cells/resolve` с `{qr}` возвращает тот же объект после
проверки текущего склада и наличия ячейки. Оба маршрута доступны только
грузчику, владельцу и менеджеру своего склада.

Формат: `argus:cell:v1:<warehouse UUID>:<cell UUID>`. QR является адресом,
не секретом и не средством авторизации. Он не доказывает физическое
нахождение человека у полки; клиент получает его со сканера или камеры.
Удалённая ячейка не подменяется новой ячейкой с похожим названием.

## Пауза и возврат

Для `POST /api/journal/pause` сохраняются прежние `invoiceId` либо `supplyId`,
`reason`, `resumed`, `exit`, `comment`. Новые события передают:

- `workSessionId` — конкретный заход, а не только документ;
- `eventSequence` — предыдущее `assembly.eventSequence + 1`;
- `eventAt` — ISO-время события с учётом смещения к `serverNow`.

Сервер не переносит старое событие на новый заход. Порядок, состояние и
время проверяются под блокировкой. Пауза и возврат учитываются по времени
событий; опоздавшая доставка отражается в журнале. Клиент отправляет их
после предыдущих складских команд того же захода. Для поступившего с
задержкой события нет обещания мгновенного уведомления без связи.

Если предыдущая команда уже завершила этот же документ и тот же собственный
заход, поздняя пауза подтверждается как `ignored: "work_finished"` без новой
записи паузы и без изменения окончания работы. Иной заход или сотрудник
по-прежнему получает конфликт.

Основные коды отказа: `work_session_changed`, `work_event_order`,
`work_event_time`, `work_event_state`, `receiving_changed`,
`placement_changed`, `addressing_changed`, `wrong_cell`,
`wrong_cell_warehouse`, `cell_not_found`, `worker_command_rejected`.

Последний код добавляется только к нетипизированному бизнес-отказу
`400`/`409` при выполнении новой команды внутри транзакции; эта транзакция
откатывается. Ошибки авторизации, повтор чужого ID и неопределённый результат
соединения/COMMIT этим кодом не помечаются.

Только явно разрешённый клиентом отказ с гарантированным откатом позволяет
после ручной сверки сохранить команду в истории как отклонённую и начать
новое действие после чтения свежего состояния. Неопределённый ответ,
`401`/`403` и `operation_changed` не подтверждают отсутствие изменения.

## Android и существующий сайт

К настроенному списку CORS добавляется только точный origin
`https://localhost`, используемый Android WebView. Остальные настроенные
origins сохраняются; это не отменяет авторизацию и серверную изоляцию.
Проверка выполняется в `test/worker-cors.test.js`.

## Проверка на отдельной базе

`node --test test/worker-commands.integration.test.js` запускается только с
явным `ARGUS_TEST_ALLOW_WRITES=1`, `DATABASE_URL` и `ADMIN_DATABASE_URL` на
`127.0.0.1:5433/argus_seller_test_worker_*`. API соединяется как `argus_app`.
Тест не читает `.env`, не запускает фоновые задачи и внешние интеграции.

`scripts/worker-local-stand.js` использует те же ограничения и запускает
только `createApp()` на `127.0.0.1:3110`. Для синтетических данных требуется
`ARGUS_WORKER_FIXTURE_PATH` вне репозитория. Значение
`ARGUS_WORKER_REUSE_FIXTURE=1` сохраняет созданный стенд при перезапуске.
